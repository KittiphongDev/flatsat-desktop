🏗️ Phase 1: The Protocol & Architecture Plan
To handle resumable images and dynamic beacons without freezing the Arduino, everything must be non-blocking.

1. The Communication Protocol
Instead of sending raw text, the OBC and GS will communicate using strict binary packets.

Packet Structure: [Sync Bytes] [Packet Type] [Payload Length] [Payload (Encrypted)] [Checksum/CRC]

Dynamic Beacon Logic: Every time the GS receives a beacon, it sends an ACK packet back. If the OBC receives an ACK, it sets the beacon timer to 1000ms. If 15 seconds pass without an ACK, the timer reverts to 10000ms.

Resumable Download Logic: The image transfer uses a "Chunk Request" system.

GS requests: DOWNLOAD "img_01.jpg"

OBC replies with file size and CRC32.

GS requests: SEND_CHUNK 0 (e.g., bytes 0-127).

OBC sends chunk. GS verifies chunk CRC.

If connection drops, the GS remembers it has up to chunk 45. When the link returns, GS simply requests: SEND_CHUNK 46. The OBC resumes instantly.

2. Dashboard to GS Mapping
Your Flutter dashboard will connect to your C++ GS via a local TCP socket.

Telemetry Cards: Parses Beacon packets (Battery, Temps, OBC state, Link Status).

Command Console: Sends UI button clicks (Ping, Reboot, Toggle Camera) to the C++ GS, which packages them into binary commands for the radio.

Parses incoming packets, decrypts them, verifies the CRC, and updates a shared state memory.Beacon Monitor: Automatically replies with an ACK packet immediately upon receiving a valid Beacon, ensuring the FlatSat switches to the 1-second interval.Image Downloader: Manages the resumable state.GS Logic: expected_chunk = 0. Send REQ_CHUNK 0. Wait for reply. If CRC matches, write to file, expected_chunk++. If timeout or CRC fails, request REQ_CHUNK 0 again.Flutter Bridge: Runs a local TCP Server or WebSocket.
